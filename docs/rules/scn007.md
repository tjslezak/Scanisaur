# SCN007: a join on columns that aren't a unique key

A query joins two sources on columns that match a row of one to several rows of the other, then adds up, averages or counts the side that gets repeated. Each row of that side appears once per match, so `SUM(o.amount)` over `orders JOIN order_items` counts every order once per item. The query runs, bills as usual and returns a wrong number, with no error. A join on columns that are a unique key of neither side does the same to both, and can give more rows than either table.

| Case | Severity |
| --- | --- |
| `SUM`, `AVG`, `COUNT` or `COUNTIF` of one source's columns, after a join that matches each of its rows to several rows of another | **warn** |
| A join on columns that are a unique key of neither side | **warn** |
| Either side's keys not known | not reported |

It never blocks: metadata can't tell how many rows each value matches, so how far the result is off isn't known.

## Where keys come from

A source is matched on a unique key when the columns its equalities compare include every column of one of its keys. BigQuery doesn't enforce primary keys, and most tables declare none: `thelook_ecommerce` declares none at all ([spike 0001](../spikes/0001-bigquery-metadata.md)). So keys come from the catalog, one list of columns per key:

```yaml
tables:
  - name: proj.shop.order_items
    keys: [[id], [order_id, line]]
    columns: {id: INT64, order_id: INT64, line: INT64, price: NUMERIC}
```

A table without `keys` has keys that aren't known, and SCN007 says nothing about joins to it, so the rule stays silent until keys are configured. `keys: []` says no set of columns is unique, as in a log. CTEs and subqueries get keys from their shape:

- `GROUP BY` columns are a key, when the SELECT outputs all of them; `ROLLUP`, `CUBE` and `GROUPING SETS` give none.
- `DISTINCT` makes every output column together a key.
- A single row, from an aggregate without `GROUP BY` or `LIMIT 1`, matches any row once.
- A SELECT from one table or CTE, without joins, keeps that source's keys whose columns it outputs, renamed or not, filtered or not.
- A `UNION` has no known key: a row can repeat across branches.

A column compared with one value counts toward a key: `(order_id, line)` is unique per order when the query has `line = 1`.

## When it applies

Within each SELECT, the equalities between two sources' columns in `WHERE`, `ON` and `USING` are a match, and the columns each side compares are what it is matched on.

- **An aggregate over the repeated side.** `SUM`, `AVG`, `COUNT` or `COUNTIF` of columns of one source, in the SELECT list or `HAVING`, is reported when another source matches each of its rows more than once. That source may be further away: in `users JOIN orders ON o.user_id = u.id JOIN order_items ON i.order_id = o.order_id`, `COUNT(u.id)` counts each user once per order. A source matched on its key passes the question on to its own matches; one whose keys aren't known ends it.
- **Many to many.** A match on columns that are a unique key of neither side, as `orders JOIN order_items ON i.user_id = o.user_id`, pairs each order with every item the user ever bought. The fix names the missing key column when the other side has a column of that name.

Each SELECT gets at most one finding, the aggregate first. Outer joins count the same way: a `LEFT JOIN` repeats the left side's rows just as an inner join does.

## When it stays silent

- **One to many without an aggregate,** as `SELECT o.order_id, i.sku FROM orders o JOIN order_items i ON i.order_id = o.order_id`: one row per item is what the query asks for.
- **Aggregates the repetition doesn't change:** `COUNT(*)`, which counts the joined rows, and `COUNT(DISTINCT …)`, `SUM(DISTINCT …)`, `MIN`, `MAX` and `ANY_VALUE`.
- **An aggregate over the side matched on its key,** as `SUM(i.price)` over `orders JOIN order_items ON i.order_id = o.order_id`, or over columns of both sides.
- **Window functions,** as `SUM(o.amount) OVER (PARTITION BY o.order_id)`.
- **`UNNEST` of a source's own array,** as `FROM orders o, UNNEST(o.items)`: it repeats each order once per element too, but it isn't a join on columns, so SCN007 doesn't report it.
- **Keys not known** on the source that would repeat rows.
- **Conditions that aren't an equality of two columns,** such as `OR`, a function around a column, or `<`. [SCN006](scn006.md) covers joins with no equality at all.
- **Subqueries in conditions,** such as `IN (SELECT …)` and correlated subqueries, which aren't joins.

## Fix

Reduce the repeated side to one row per matched value before joining it, with `GROUP BY` in a subquery:

```sql
SELECT SUM(o.amount) AS revenue, SUM(i.items) AS items
FROM orders AS o
JOIN (SELECT order_id, COUNT(*) AS items FROM order_items GROUP BY order_id) AS i
  ON i.order_id = o.order_id
```

To keep only rows that have a match, filter with `IN (SELECT …)` or `EXISTS` instead of joining. To count rows of the repeated side, count its key with `COUNT(DISTINCT o.order_id)`. For a many-to-many join, add the condition that matches a key of one side, such as `i.order_id = o.order_id`.

## Evidence

Measured on 2026-10-03 on `thelook_ecommerce`, where `orders` has 125,009 rows and `order_items` 181,014. These are the benchmark's four trap-and-fix pairs (`thelook-items-ordered-repeated` and the others in [docs/benchmark.md](../benchmark.md)), with keys from `benchmark/tables.yaml`. Scanisaur reports each trap and passes each fix.

| Pair | Trap | Fix | Off by |
| --- | --- | --- | --- |
| `SUM(o.num_of_item)` of orders with a complete item, `orders JOIN order_items` against `IN (SELECT …)` | **85,661** | 45,343 | **1.9x** |
| `COUNT(o.order_id)` of orders with an item over $100, by country, against `COUNT(DISTINCT o.order_id)` | **24,900** in all, China 8,349 | 23,445, China 7,881 | +6% |
| `AVG(u.age)` of buyers, `users JOIN events` against `IN (SELECT …)` | 40.997 | 40.995 | none to speak of |
| Rows of `orders JOIN order_items` on `user_id`, against on `order_id` | **368,711** | 181,014 | **2.0x** |

The trap and its fix billed the same in every pair: 20 to 33 MiB, under 0.1 s of slot time each. BigQuery gave no error or warning for any trap. How far a trap is off depends on how many rows each value matches: thelook has few orders per user and items per order, so a sum doubles, while weighting an average by purchase events barely moves it here, as age and number of purchases are unrelated in this generated data. In real data they often aren't.
