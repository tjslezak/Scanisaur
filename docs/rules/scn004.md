# SCN004: a function stops BigQuery from skipping data

A filter wraps a partition or cluster column in a function that BigQuery can't see through, so the filter doesn't limit what is read.

| Column | Severity |
| --- | --- |
| Partition column of a table that requires a partition filter | **block**: BigQuery rejects the query |
| Partition column of another table, 1 GiB or larger, or of unknown size | **warn** |
| Cluster column of a table 1 GiB or larger, or of unknown size | **warn** |
| Either, on a table smaller than 1 GiB | **info** |

A partition-column finding appears only when no other filter limits the partitions: `CAST(d AS STRING) LIKE '2026-09%' AND d >= '2026-09-01'` is fine. A cluster-column finding appears only when no plain filter on the same column exists. The defeating function can sit under `=`, a range, `IN` or `LIKE`.

## Which functions defeat pruning

BigQuery sees through more functions than you might expect, so Scanisaur flags only those measured to defeat pruning. A function not in these tables is assumed to prune. Measured with dry runs on public tables on 2026-10-02.

**Partition columns** ("—" means not measured)

| Function | `DATE` column | `TIMESTAMP` column |
| --- | --- | --- |
| `DATE()`, `DATE(ts, timezone)`, `CAST(… AS DATE)`, `EXTRACT(DATE FROM …)`, `DATE_TRUNC(DATE(ts), MONTH)` | — | Prunes |
| `TIMESTAMP_TRUNC`, `TIMESTAMP_ADD`, `FORMAT_TIMESTAMP`, `EXTRACT(YEAR FROM …)` | — | Prunes |
| `DATE_TRUNC`, `DATE_ADD`, `TIMESTAMP(date)` | Prunes | — |
| `FORMAT_DATE` | **Defeats** | — |
| `CAST(… AS STRING)` | **Defeats** | **Defeats** |
| `EXTRACT` of `MONTH`, `DAY` or `DAYOFWEEK` | **Defeats** | **Defeats** (`MONTH`) |
| `EXTRACT` of `DAYOFYEAR`, `WEEK` or `QUARTER` | — | **Defeats** |
| `UNIX_SECONDS`, `UNIX_MILLIS`, `DATETIME(ts)` | — | **Defeats** |

Scanisaur flags each defeating function on the column types where it applies, and treats `SAFE_CAST(… AS STRING)` like `CAST`. A cast to STRING on an integer-range partition hasn't been measured, so it isn't flagged. `UNIX_DATE` pruned partially in one test, so it isn't flagged.

**Cluster columns**

| Function | Effect |
| --- | --- |
| `LOWER`, `UPPER`, `TRIM` | **Defeats**: one PyPI day reads 98.5 GB with `LOWER(project)`, against 0.84 GB with `project = 'requests'` and 39 GB with no cluster filter |
| `SUBSTR(x, 1, n)`, `LIKE 'prefix%'` | Prunes, so a plain `LIKE 'prefix%'` on the column counts as using the clustering; `NOT LIKE` doesn't |

**`_TABLE_SUFFIX`:** every wrapper measured prunes, so SCN004 never applies to it.

## Not reported

Queries with an outer `LIMIT 0`, which return only the schema. BigQuery reads nothing and accepts them, measured on 2026-10-02 with `CAST(datehour AS STRING)` on a table that requires a partition filter.

## Fixes

Where the function can simply be dropped, the fix shows the rewritten filter. A cast to STRING is dropped only on a `DATE` column compared with whole dates: `CAST(d AS STRING) = '2026-09-30'` becomes `d = '2026-09-30'`. For cluster columns only the defeating function goes: `SUBSTR(LOWER(project), 1, 3) = 'req'` becomes `SUBSTR(project, 1, 3) = 'req'`, correct only if the stored values use that case. Otherwise the fix suggests comparing the column with a constant.

Conditions in messages are shown as sqlglot writes them, which can differ from the original: `FORMAT_DATE('%Y-%m-%d', d)` appears as `FORMAT_DATE('%F', d)`, an equivalent format.
