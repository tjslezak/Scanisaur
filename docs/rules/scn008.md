# SCN008: a comparison between different types

A join or filter compares two values of different types. BigQuery either refuses the comparison, so the query fails, or converts one side in a way that changes the answer while the query runs normally. The second kind is the one that matters most: nothing tells the agent the number it got back is wrong.

| What the comparison does | Example | Severity |
| --- | --- | --- |
| A date against a `TIMESTAMP` or `DATETIME`, read as midnight, where the time of day changes which rows match | `created_at <= '2024-09-30'`, `created_at = '2024-09-30'` | **warn** |
| `INT64`, `NUMERIC` or `BIGNUMERIC` equal to a `FLOAT64`, both read from data | `v.visitor_id = c.visitor_id` | **warn** |
| Types BigQuery refuses to compare | `user_id = 42` on a `STRING` column, `event_ts > CURRENT_DATE()` | **warn** |

## Evidence

Measured on 2026-10-03, with dry runs and with queries over literals only, which bill nothing.

| Query | Result |
| --- | --- |
| `TIMESTAMP '2024-09-30 15:00:00' <= '2024-09-30'` | **false**: the date is midnight UTC, so the rest of the day is left out |
| `TIMESTAMP '2024-09-30 15:00:00' BETWEEN '2024-09-01' AND '2024-09-30'` | **false** |
| `DATETIME '2024-09-30 15:00:00' = DATE '2024-09-30'` | **false**: the DATE becomes midnight |
| `CAST(9007199254740993 AS INT64) = CAST(9007199254740992 AS FLOAT64)` | **true**: two different IDs match |
| `CAST(9007199254740993 AS INT64) = CAST(9007199254740992 AS NUMERIC)` | false |
| `INT64 = STRING`, `STRING = 123`, `INT64 = '123'`, `STRING IN (1, 2)` | "No matching signature for operator =" (or `IN`) |
| `DATE = TIMESTAMP`, `TIMESTAMP > CURRENT_DATE()`, `DATETIME = TIMESTAMP`, `TIME = DATETIME` | "No matching signature" |
| `BYTES = STRING`, `BOOL = INT64`, `STRING = DATE` (a column, not a literal) | "No matching signature" |
| `DATE = DATETIME`, `INT64 = FLOAT64`, `NUMERIC = FLOAT64`, `INT64 = 1.5` | accepted |
| `pageviews_2025 WHERE datehour = '2025-06-01' AND …` (dry run) | accepted, 423 MB: it runs, and sums one hour of the day |

A string literal converts to `DATE`, `DATETIME`, `TIMESTAMP` or `TIME` when its text reads as one, but never to a number, `BOOL` or `BYTES`.

## When it applies

Every comparison in `WHERE`, `ON`, `HAVING` and `QUALIFY`, in the outer query, CTEs and subqueries alike: `=`, `!=`, `<`, `<=`, `>`, `>=`, `IS NOT DISTINCT FROM`, `BETWEEN` and `IN` with a list. Types come from the catalog's columns, struct fields included, through CTEs and subqueries, and from literals, casts and functions.

- **A date against a moment.** A string literal holding just a date, as `'2024-09-30'`, against a `TIMESTAMP` or `DATETIME`, or a `DATE` value against a `DATETIME`. With `<=`, `>`, the end of a `BETWEEN`, `=`, `!=` or `IN`, the time of day changes the answer. The fix gives the half-open form, such as `created_at < '2024-10-01'` for `created_at <= '2024-09-30'`.
- **Whole numbers against `FLOAT64`.** An equality between an exact number and a `FLOAT64`, neither of them a constant, as a join key loaded as `FLOAT64` on one side. BigQuery converts both sides to `FLOAT64`, which holds whole numbers exactly only up to 2^53, so larger IDs that differ can match.
- **Refused types.** BigQuery fails the query before it reads anything. The finding saves a round trip and names a conversion.

## When it stays silent

- **Whole days either way:** `>=` a date, and `<` a date, start or stop at midnight, which is what they mean. So does a moment truncated to a day or coarser (`TIMESTAMP_TRUNC(ts, DAY)`, `DATETIME_TRUNC(dt, MONTH)`) or made from a `DATE` (`TIMESTAMP(day)`, `CAST(day AS DATETIME)`), and `DATE(ts)` on the column.
- **A literal with a time of day,** as `'2024-09-30 23:59:59'`.
- **`FLOAT64` against a constant,** as `score = 1`, and comparisons that aren't equalities, as `score < amount`.
- **Types that aren't known:** query parameters such as `@user`, `NULL`, arrays and structs, and an `IN` over a subquery or `UNNEST`.
- **The `SELECT` list:** a `CASE WHEN` there isn't a join or a filter.
- **`LIMIT 0`** returns no rows, so only refused comparisons are reported: BigQuery still compiles them.

## Fix

- A date against a moment: compare with the next day, as `created_at < '2024-10-01'`, or compare days, as `DATE(created_at) = '2024-09-30'`. Both still let BigQuery skip partitions.
- Whole numbers against `FLOAT64`: cast the `FLOAT64` side to the exact type, as `CAST(v.visitor_id AS INT64)`.
- Refused types: write the literal in the column's type, as `user_id = '42'` on a `STRING` column, or convert one side with `CAST`, `DATE()` or `TIMESTAMP()`.
