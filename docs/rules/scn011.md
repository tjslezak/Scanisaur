# SCN011: a cluster filter without the leading cluster column

A query filters a later cluster column of a table clustered by two or more columns, but not the first. BigQuery sorts clustered data by the cluster columns in order, so a filter on a later column alone may skip far fewer blocks. Unless something else limits it, the result also covers every value of the leading column, which may not be what the question asked.

| Table | Severity |
| --- | --- |
| 1 GiB or larger, or of unknown size | **warn** |
| Smaller than 1 GiB | **info** |

## Evidence

Billed bytes, measured on public tables on 2026-10-01 ([#14](https://github.com/tjslezak/Scanisaur/issues/14)):

| Query | Billed | Answer |
| --- | --- | --- |
| Wikipedia pageviews, one day, clustered by `wiki`, `title`: `wiki = 'en' AND title = 'Python_(programming_language)'` | 810 MB | 1,891 |
| The same with `title` only | **6.68 GB**, against 3.41 GB with no cluster filter (dry run) | **3,276** |
| deps.dev package versions, one snapshot, clustered by `System`, `Name`: `System = 'PYPI' AND Name = 'requests'` | 44 MB | 161 |
| The same with `Name` only | **230 MB**, against 4.2 GB with no cluster filter (dry run) | **199** |

How much a missing leading filter costs depends on how many distinct values the leading column has, which table metadata doesn't give. Without `wiki`, the query cost more than with no cluster filter at all, because it also read the `title` column. Without `System`, it still skipped most blocks. Both answers changed, because the question widened to every wiki or every package ecosystem.

## When it applies

- **A filter that picks values of a later column:** the column compared with constants by `=` or `IN`, or an `OR` of them, as measured. The column may sit under `LOWER`, `UPPER` or `TRIM`. Filters in `WHERE`, an inner join's `ON` and `HAVING` on a grouping column count, and so do filters written on a CTE or subquery over the table. `QUALIFY` runs too late to skip blocks, so it doesn't count.
- **No filter on the leading column** that confines it to values, ranges or a prefix. A filter wrapped in a function, such as `LOWER(wiki) = 'en'`, counts as one: [SCN004](scn004.md) reports the function instead.
- **Nothing else on the leading column, except exclusions:** `wiki != 'commons'`, `wiki NOT IN (...)`, `wiki NOT LIKE '...'` and `wiki IS NOT NULL` rule out a few values and keep nearly every block, so the rule still applies.

A query that filters a later column with a function and has no leading filter, such as `LOWER(title) = '…'` alone, gets both SCN004 and SCN011, so an agent can fix both in one rewrite.

## When it stays silent

Scanisaur stays silent when something may pick values of the leading column in a way that hasn't been measured. A wrong warning costs an agent more than a missed one.

- **Joins and subqueries on the leading column:** `JOIN wikis w ON p.wiki = w.wiki`, `wiki IN (SELECT …)`, a correlated `EXISTS (SELECT 1 FROM wikis w WHERE w.wiki = p.wiki)` in `WHERE`, `ON`, `HAVING`, `QUALIFY` or a selected column, or `INTERSECT`, written on the table or on a CTE or subquery over it. Another source picks the values while the query runs, and dry runs can't show whether BigQuery then skips blocks. This includes outer joins, which a `WHERE` filter on the other side can turn into inner joins, and self-joins.
- **Filters BigQuery can't apply while reading:** `QUALIFY wiki = 'en'`, `HAVING` on an alias or after `ROLLUP`, `wiki = 'en' OR wiki IS NULL` on the side an outer join fills with NULLs, or `WHERE wiki = 'en'` on a CTE that ends in `LIMIT` or `QUALIFY`. The answer covers one wiki even though every wiki is read.
- **Other filters on the leading column:** `wiki IN UNNEST(@wikis)`, `STARTS_WITH(wiki, 'en')`, an `OR` that mixes it with other columns, or any condition on a `BOOL` leading column, where `active != TRUE` picks the one other value.
- **Ranges, `LIKE` and other functions on a later column,** such as `title >= 'A'` or `DATE(event_ts) = '2026-09-01'`, which is a range too. These weren't measured, and a range on a later column is usually a time window over every value of the leading one. For the same reason the partition column never counts as a later cluster column: on a table partitioned by `ts` and clustered by `customer_id`, `ts`, a filter on `ts` is the partition filter. When the partition column is the leading cluster column, [SCN003](scn003.md) asks for its filter instead.
- **A gap after the leading column:** on a table clustered by `system`, `name`, `version`, a query filtering `system` and `version` but not `name` isn't reported. Within each `system` the same problem applies, but nothing has been measured yet.
- **Tables clustered by one column**, and unclustered tables.

## Fix

If the question is about particular values of the leading column, filter on them too: `wiki = 'en' AND title = 'Python_(programming_language)'`. If the question really is about every value, the finding can be ignored; the cost is the price of that question.
