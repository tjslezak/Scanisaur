# SCN003: no filter that limits partitions or shards

A query reads every partition of a partitioned table, or every shard of a wildcard table, because nothing in it lets BigQuery skip any.

| Table | Severity |
| --- | --- |
| Requires a partition filter (`require_partition_filter`) | **block**: BigQuery rejects the query |
| Partitioned or sharded, 1 GiB or larger, or of unknown size | **warn** |
| Partitioned or sharded, smaller than 1 GiB | **info**: reading all of it costs little |

## What counts as a filter that limits partitions

- **Partitioned tables:** a comparison of the partition column with constants: `=`, `<`, `<=`, `>`, `>=`, `BETWEEN` or `IN` (including `x = 'a' OR x = 'b'`). Relative dates such as `DATE_SUB(CURRENT_DATE(), INTERVAL 7 DAY)` are constants. The comparison can be wrapped in a function that still prunes (see [SCN004](scn004.md)); a function that doesn't is reported by SCN004 instead.
- **Ingestion-time tables:** the same, on `_PARTITIONTIME` or `_PARTITIONDATE`.
- **Wildcard tables:** any filter on `_TABLE_SUFFIX` that compares it with constants, wrapped or not (`PARSE_DATE`, `CAST`, `SUBSTR` and `LIKE` were measured to prune), or a narrower wildcard such as `events_2026*`.
- Filters reach the table through CTEs, subqueries and `UNION` branches, as BigQuery's planner pushes them.

These don't limit partitions: `IS NOT NULL`, `!=`, a comparison with a subquery or another column, and a filter in `QUALIFY`.

## Not reported

- `COUNT(*)` and other references that read no columns of an optional-filter table: BigQuery answers them from metadata.
- References that read only pseudo-columns, such as `SELECT DISTINCT _TABLE_SUFFIX`.

## Evidence

Measured on public tables on 2026-10-01 ([#10](https://github.com/tjslezak/Scanisaur/issues/10)):

| Query | Billed |
| --- | --- |
| Trends, filtered on `week` instead of the partition column `refresh_date` | 1.57 GB, against 58.7 MB with `refresh_date`, and 55 rows instead of 5 |
| deps.dev, no filter on the snapshot partition | 10.7 GB, against 44 MB |
| GA4, `event_date` instead of `_TABLE_SUFFIX` | 99.6 MB, against 10.5 MB |
| Trends, `refresh_date = (SELECT MAX(refresh_date) …)` | the whole table (dry run) |
| Pageviews, no filter on a table that requires one | rejected |

The message names a filter on another date column when the query has one, since that is the usual mistake.
